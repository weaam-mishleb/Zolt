### `test_cities.py` — נרמול ערים חוצה-רשתות (26 בדיקות פרמטריות)

הרשתות שולחות ערים בפורמטים שונים: שופרסל — **שמות** (עם וריאנטים), רמי לוי ואושר עד — **קודי למ"ס** מספריים. בלי נרמול, הסינון לפי עיר פשוט לא עובד.

| קבוצה | דוגמאות מאומתות |
|---|---|
| וריאנטי שמות → קנוני (‏6) | `תל אביב-יפו` / `תלאביב` / `"תל אביב"` ← תל אביב; `פתח-תקוה` ← פתח תקווה |
| קודי למ"ס → שם (‏4) | `5000` ← תל אביב; `3000` ← ירושלים; `9000` ← באר שבע; `874` ← מגדל העמק |
| קוד ריק/אפס → גזירה משם הסניף (‏3) | `"", "רגר באר שבע"` ← באר שבע; `"רמות"` ← ירושלים (שכונה) |
| שם לא מוכר עובר נקי, ללא מיפוי שגוי (‏5) | `גבעתיים` ← גבעתיים; קוד לא מוכר ← None |
| איחוד כפילויות רווחים/מקפים (‏8) | `אור-יהודה`/`אוריהודה` ← אור יהודה; `בני  ברק` ← בני ברק |

**הרצה:** `make test` או `SCHEDULER_ENABLED=false python -m pytest backend/tests -q` → `35 passed`.

## 2. בדיקות אינטגרציה — Test Plan ‏TC-1..TC-10 (`scripts/run_test_plan.py`)

רצות דרך **FastAPI TestClient מול MySQL אמיתי** — מפעילות את כל השרשרת: ולידציית Pydantic → routers → services → SQL. תרחישי ה-DB ההרסניים (TC-6) עטופים בטרנזקציה עם **rollback** כדי לא לזהם נתונים.

| TC | תרחיש | שיטה | תוצאה מצופה | תוצאה אחרונה |
|---|---|---|---|---|
| TC-1 | סל תקין — סכום ודירוג | ‏3 מוצרים ×[2,1,1] בתל אביב → `POST /basket/compare` | ‏200; סניפים שלמים ממוינים מהזול ליקר | ✅ PASS — ‏19 סניפים, מנצח 105 |
| TC-2 | כמות שלילית | `quantity: -1` | ‏400 + הודעה ברורה | ✅ PASS |
| TC-3 | סל ריק | `items: []` | ‏400 + הודעה ברורה | ✅ PASS |
| TC-4 | מוצר חסר לא זוכה | עיר בה סניף חסר פריט | הסניף החלקי `rank=None`; מנצח שלם בלבד | ✅ PASS (אופקים) |
| TC-5 | **תקציב זיכרון ETL** | ‏ETL מלא (85MB, ‏489K שורות) תחת `/usr/bin/time -l` | שיא RSS ‏< 100MB | ✅ PASS — **89MB, ‏29.6s** |
| TC-6 | ‏Upsert בלי כפילות | שינוי מחיר + ‏upsert חוזר לאותו (product,store) | עדיין שורה אחת; המחיר עודכן (rollback בסוף) | ✅ PASS |
| TC-7 | שורת CSV פגומה | קובץ 2,000 שורות עם שורה משובשת באמצע | ‏1,999 שורות נקראות — השורה הפגומה מדולגת, לא מפילה | ✅ PASS |
| TC-8 | חיפוש עברית במונח אנגלי | `GET /products/search?q=milk` | ‏200 + רשימה ריקה (graceful, לא שגיאה) | ✅ PASS |

### שני מצבי הרצה

```bash
# מול ה-DB הענני (ברירת המחדל של .env) — TC-5 מדלג בחיבור ביתי איטי (צוואר בקבוק רשת, לא זיכרון)
python -m scripts.run_test_plan                      # → PASS=9, SKIP=1

# מול DB מקומי (Docker) — המדידה המלאה, כולל TC-5
docker compose up -d
DATABASE_URL="mysql://zolt:zolt_pass@127.0.0.1:3306/zolt" SCHEDULER_ENABLED=false \
  python -m scripts.run_test_plan                    # → PASS=10
```

‏TC-5 מבחין במכוון בין **כשל הדרישה** (זיכרון חרג → FAIL) לבין **כשל מדידה סביבתי** (‏timeout רשתי מול ענן → SKIP) — בדיקה שמסמנת FAIL על רשת איטית הייתה משקרת.

## 3. השכבה התפעולית — בדיקות רציפות בפרודקשן

- **`GET /health`** — מאמת חיבור DB חי עם **תקציב זמן קשיח של 5 שניות**: ‏DB תקין → ‏200 `{"db":"up"}`; תקוע → ‏503 `{"db":"timeout"}` מהיר במקום בקשה תלויה (לקח מתחקיר "אינסטנס הזומבי" — בקשה תלויה חסמה shutdown והפילה את השירות). מנוטר ע"י UptimeRobot כל 5 דקות.
- **`etl_jobs`** — כל ריצת ETL מתועדת: סטטוס, ‏% התקדמות, זמנים, שגיאות. זיהוי ריצה תקועה (stale) אוטומטי אחרי 15 דקות ללא עדכון. נצפה בפאנל הניהול (FR-1.5, FR-5.4).
